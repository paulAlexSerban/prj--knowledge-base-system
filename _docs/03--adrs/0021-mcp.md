# ADR 0021: FastMCP, beside the REST API

Status: decided during the build.

## Context

A second agent should not need a custom integration. MCP is the tool protocol those clients already speak. It does not authenticate the caller and it does not enforce access.

## Decision

The MCP server depends on `fastmcp>=4.1.0` and builds `FastMCP` with a `TokenVerifier` that validates the HS256 token. FastMCP 4 runs on the official `mcp` 2 package. The process listens on port 8001. Tools are `search_knowledge`, `get_document`, `find_related`, and `list_sources`. There is no write tool. Tool text says the snippet is untrusted data. `gateway-core` is the service layer. The REST API on port 8000 is the other adapter. Tool schemas live next to that layer so the two cannot drift. REST `list_sources` is public. MCP requires a bearer token on `/mcp`, including for `list_sources`.

## Alternatives rejected

- REST only. Enough for the chat page, which is what calls it. A notebook agent would then invent its own tool protocol. MCP is the one those notebooks already speak.
- A hand-rolled tool protocol. The same shapes, with none of the clients.
- The official `mcp` SDK server class (`MCPServer`). It worked and was the first implementation. FastMCP gives the same tools with less glue: decorator tools, a `TokenVerifier` base, `custom_route`, and middleware passed to `run`. The notebooks already use the FastMCP client, so one library covers both sides.
- Treating "the client speaks MCP" as "the call is allowed". Rejected in [ADR 0018](0018-authorization.md).

## Consequences

- MCP clients and the chat page can diverge in which tool they pick. The query router that would stop that is not built. Notebooks `50` and `51` print the model's choice.
- FastMCP is a third-party layer over the official package and has changed its structure between major versions. The version is pinned in `uv.lock`.
- The tests call tools over the real transport as a persona, because the auth context exists only there.
